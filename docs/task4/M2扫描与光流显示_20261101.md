## 光流视频底图

旧综合观测台 `host/index.html` 的光流画布此前只绘制矢量。现在复用已经打开的 PC 视频流作为底图；PC 视频不可用时，使用新鲜的 Nano 推理画面。没有再开一个 UDP 接收器或额外 MJPEG 连接。

图传是 320×320，其中上下各70行是留边；中间320×180对应光流160×90坐标。页面裁出这个有效区域再绘制至640×360，光流位置放大4倍、位移箭头额外放大4倍。底图随浏览器动画节拍刷新，元数据仍按200ms轮询。失联/过期时清除旧底图、矢量及雷达扫描。

底图采用最新视频，**与光流结果未逐帧锁定**，页面已明确标注。它用于实时观测，不可拿显示上的瞬时重合误差当作算法误差测量。

## M2 雷达显示链路

```text
STL-27L TX → M2-14/B16 → 921600 UART → 原始CRC/格式解析器
                                         ├→ 全部点 → 原导航/近障保护
                                         └→ 显示旁路 → 72扇区 → 混合115200遥测
                                                                    ├→ 任务四诊断台
                                                                    └→ Nano网关 → 原8872综合观测台
```

显示旁路不改变原始解析器、导航点流、ARM或看门狗。每个5°扇区保留一圈内非零距离/强度的最近回波，未知扇区为0。它是低带宽扫描概览，不是所有原始雷达点。

启动后先等待跨零，再收集完整一圈；角度间隔超过10°、该圈有接收错误、点流中断超过250ms，均不发布为有效圈。完成圈要求至少60个扇区被角度采样访问，诊断的coverage指角度访问覆盖数，不是有效距离数。扫描发送最高5Hz，每圈六片，连续发送期间快照保持不变；读取端阻塞时不反压导航，超过400ms放弃未发完的显示扫描。

串口已有20Hz电机、约100Hz编码器诊断/轨迹、50Hz IMU及10Hz导航摘要；扫描最高30片/s、接收诊断5片/s，总上限约215个48字节帧/s，约103.2kbit/s（8N1），低于115200。新增辅助通道ready握手，避免IMU/导航定时快照覆盖扫描分片；电机及编码器遥测仍保留原优先级。

## 新增串口帧

所有新增帧48字节，整数低字节先传；末尾CRC16-CCITT-FALSE，初值0xFFFF，校验前46字节，CRC低字节先传。旧协议、操作码和波特率不变。

### `C3 3C 05 01`：扫描分片

| 字节 | 内容 |
|---|---|
| 4–5 | 16位扫描序号，允许回绕 |
| 6 | 分片索引0..5 |
| 7 | 固定6片 |
| 8–9 | 生成该分片时扫描快照的帧龄，ms |
| 10–45 | 12组 `{distance_mm:u16, intensity:u8}` |
| 46–47 | CRC16 |

扇区索引=`分片索引×12+片内索引`，显示角度为扇区中心 `索引×5°+2.5°`。PC/Nano只在六片齐全且序号前进时发布扫描；缺片、重复、迟到旧帧不会刷新扫描新鲜度。设备帧龄与接收端等待时间共同参与500ms过期判断。

### `C3 3C 06 01`：接收诊断，约5Hz

| 字节 | 内容 |
|---|---|
| 4–5 | 最近显示扫描序号 |
| 6 | bit0近期有点、bit1收集一圈中、bit2本圈异常、bit3扫描发送中、bit4曾完成有效圈 |
| 7 | 保留0 |
| 8–11 | 设备运行ms |
| 12–15 | UART成功接收字节数 |
| 16–19 | UART停止位错误数 |
| 20–23 | 有效雷达包数 |
| 24–27 | 雷达CRC错误数 |
| 28–31 | 雷达格式错误数 |
| 32–35 | 半包超时数 |
| 36–39 | 有效完整圈数 |
| 40–43 | 因限频/发送忙而未上传的有效圈数 |
| 44–45 | 最近有效圈的角度访问覆盖扇区数 |
| 46–47 | CRC16 |

错误计数均来自原接收阶段，不把聚合错误全部标成CRC错误。只收到诊断不等于收到完整扫描。两套页面均显示接收字节、包数、停止位/CRC/格式/超时及诊断帧龄。

## 配置与启动

原8872页面的USB雷达路径保留，`lidar_source: "usb"` 为兼容默认值。M2必须使用 `config/nano.m2.example.json` 的配置：

```json
{"lidar_enabled": true, "lidar_source": "fpga"}
```

该模式只打开FPGA的115200串口，不再打开独立的921600雷达USB串口。填好实际FPGA稳定串口路径、令牌及网关地址，再按原运行说明启动网关与综合观测台。不能与任务四串口诊断台或任务CLI同时占用同一个UART。

任务四诊断台仍可独立读取或回放混合UART，新扫描图不要求导航START；保持未ARM也可以检查雷达。

下一次静态实机检查，可在电机12V断开、正确M2候选已装载、其他串口所有者正常退出后执行：

```powershell
python tools/task4/verify_lidar.py --serial COM实际端口 --seconds 10 --out runs/m2_lidar_新目录
```

此工具只读串口，不发送STOP、CLEAR、ARM、心跳或导航命令。保存 `rx.bin`、`chunks.jsonl` 和 `result.json`；通过要求字节/有效包推进、至少两次完整新扫描、电机全窗口未ARM且零输出、末端遥测新鲜、混流CRC为0。故障上下文可用 `--replay <chunks.jsonl>` 离线复核，回放明确标记未测试硬件。

最终结果及对应源码哈希保存在本目录 `evidence/m2_scan_20261101/`。浏览器可视检查使用醒目标注的合成视频/扫描；未把页面演示当作实物雷达结果。新固件时序、下载与硬件验收状态以该证据目录汇总为准，不能沿用10月31日旧位流的通过记录。

## 本轮最终结果

68项Python、页面脚本与两套页面合成数据可视检查通过；10组电机RTL回归通过。任务四完整回归通过，含1083组算术、226组VFH、原始雷达接收及扫描上传端到端检查；完整顶层收到6片扫描和1条接收诊断，混流CRC为0，72个扇区逐项正确，STOP后保持零输出。记录见 `evidence/m2_scan_20261101/summary.json`。

完整综合通过；初次及布线尝试重新综合后的网表均通过control50连接与唯一LK状态寄存器审计。两份网表哈希不同，审计分别保留，不混用。Place3/Route0布线在1200秒上限退出，未生成新位流、没有新的Setup/Hold通过结论。旧候选的MPW −0.688ns等未决项也未在本轮解决。不得直接沿用旧M2位流作为新扫描协议的实机验证；后续先完成新候选PnR与时序审阅，再恢复静态上板接收检查。
