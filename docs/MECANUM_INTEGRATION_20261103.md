## 当前接入范围

四轮位置闭环、定角、任意角度平移、MPU6050/6500、摄像头、光流、视觉事件、360 扇区最近回波雷达。
相机、光流和以太网源码沿用已提交基线，没有为本次集成修改它们的时序实现。

旧 `nav_core` 用双轮里程计及左右轮目标，不适用于四轮横移。因此新顶层使用队友的麦轮相对位置闭环，
**没有启用旧的双轮自动导航/避障驱动**。这部分需另行移植运动模型，不能把左右轮命令直接复制到四个轮子。

IMU 总线由队友驱动独占：100 Hz 陀螺采样、20 Hz P4 姿态遥测，不启用原整机的 1 kHz 九轴字段接口。
沿用队友的断线保留最近航向策略：首次校准完成后，缺帧不单独触发 IMU 停车，P4 仍报告过旧及通信错误。
不会积分断线期间的未知运动；串口命令 250 ms 看门狗、STOP、四轮故障停车继续存在。
这与原主工程的 IMU 超时策略不同，是明确保留的队友行为，并非已完成的两种策略统一。

## 协议与接收端

控制：UART 115200/8N1，V3 24 字节。只保留 0 STOP、1 ARM、3 CLEAR、6 POSE、7 KEEPALIVE、8 IMU 重连校零。
2/4/5 已取消，不重新引入遥控、单轮或保持朝向速度模式。方向保留字段必须为 0。

状态：UDP 6205，现有 TLM1 外封装，内含 48 字节 M4/P4 或雷达帧。M4/P4 为小端 CRC，旧 IMU 帧仍为大端 CRC，
接收器按包头分别处理。`frame_uart_mux` 保持完整活动帧直到网口握手完成；周期快照拥塞时保留较新的待发送值。
全部状态走网口，整机 UART TX 空闲。相机/光流/视觉事件沿用原独立 UDP 通道。

PC 调试入口（运行时需 pyserial；离线测试不接设备）：

```powershell
python host/mecanum/gui.py --telemetry-bind 192.168.50.10
python host/mecanum/console.py --port COMxx --action monitor --telemetry-bind 192.168.50.10
```

GUI 保持默认离线；连接后从 UDP 收状态、从选定串口发命令。监测 CLI 不主动发运动命令。
上述 PC 入口需要 FPGA 的遥测目标已指向 PC；默认硬件网络配置可能仍指向 Nano。
不自动改网络目标。现有 `tools/task4/telemetry_endpoint.py` 可在硬件联调时配置目标，注意它也影响视频目标，须与图传使用方协调。
同一台机器的 GUI 和独立接收器不能同时占用 6205。

Nano：`config/nano.mecanum.ethernet.example.json`，只接收并在 `/api/state` 的 `mecanum` 字段导出四轮及姿态，
旧双轮 HTTP 控制接口明确拒绝命令，不打开命令串口。PC 调试时若改遥测目标到 PC，Nano 不会同时收到该单播。
本次没有部署 Nano 服务，也没有修改正在使用的串口/网口配置。

## 离线验证与构建

```powershell
python tools/mecanum/test.py
python tools/mecanum/build.py
# 上一条输出冻结目录，再传给整机仿真：
python tools/mecanum/test_system.py <冻结目录>
```

`test.py` 在导入后的 RTL 上运行队友测试（24 个 bench）以及集成背压测试，共 25 组；另运行原 28 项上位机测试及新增协议测试。
上游 `tools/test.py` 漏带 `tb_pose_serial_top` 需要的 MPU 模型；本入口显式加入模型，并用 `-s` 限定仿真根，快照原件保持不改。

整机测试含实际 MPU6500 I²C 模型、1000 个合成雷达包及一个损坏包、独立最近回波参考、视频并发、内外 CRC、四轮未使能输出和 UART 空闲检查。
PHY 初始化和视频字节沿用原测试的注入方法；这不能证明实际 PHY 启动或摄像头电气链路正常。

构建脚本只生成冻结源码、GPRJ/CST/SDC、引脚审计与 `build.tcl`，不抢占高云进程、不下载。
真实综合后的同步器名字、SDC 命中、完整时序和资源占用尚需检查，不能据离线仿真判定时序通过。
以太网基线本身仍有已记录的 6 个 setup/recovery 违例以及脉宽/PR1014 问题，另一智能体正在优化。
