# 1kHz 整机构建超时与 RTL 检查（2026-11-03）

## 结论

新增控制逻辑有可优化的资源和组合路径，但现有证据不足以认定它是本次超时的直接原因。
首次超时的日志已走完布线、时序分析，停在 Bitstream generation in progress；包装脚本按总时长 1800 秒终止进程。
因此“超时”等于构建超过脚本预算，并不等于控制回路超时、布线失败或已确认工具死锁。
旧版整机耗时 538.8 秒；所查目录 9 个 result.json 中，8 个未标记超时，1 个标记超时。
其余旧整机记录多数约 483～655 秒，另有一个 151 秒记录。未超时不代表全部通过时序验收。

## 按优先级检查结果

1. **构建记录缺少阶段耗时，超时后未区分阶段。**
   `tools/task4/build_ethernet.py:174-191` 只检查总时长和最终完成标志；
   超时结果未保存当前阶段、阶段起始时间、子进程 CPU 增量和输出文件是否持续增长。
   这使“正常但较慢”和“位流生成停滞”难以区分。
   建议记录综合、布局、布线、时序、位流生成阶段的时间及产物变化，再据此设置预算。
   第一次超时已经完成 P&R，从头重跑 P&R 会重复消耗时间；是否能安全从后续阶段恢复，需先核对工具流程及产物完整性。
   不能以不完整 `.fs` 存在来宣称成功，也不应仅延长超时就称问题已修复。

2. **四路轮速估计器是明确的新增资源热点。**
   `fpga/motor/wheel_speed_hybrid.sv:13-14,27-31,81-88` 使用两个 8 深度数组和动态索引，
   综合后每路 768 个 DFFCE、9 个 DFFPE，四路合计 **3108 个寄存器**；
   四路还有 **384 个 MUX2_LUT5、192 个 MUX2_LUT6、1328 个 ALU**。
   这些是模块总量，不能全部归因于数组，但确认数组并未直接变成 BSRAM。
   `new_rolling` 还将历史桶选择、减法、加法、常数乘 320 放在同一结果路径上。
   建议先把历史桶读出、滚动和更新、速度归一化拆成流水阶段；
   对桶宽度依据最大编码器速率与异常处理重新推导，再决定缩位或改变存储形式。
   不应在未证明边界前直接截断到 16 位，也不必为仅 8 深度历史桶盲目换 BSRAM。
   目前估计器在 1ms 后还有 40 个时钟的固定等待；增加流水必须同步核对该反馈有效时刻。

3. **PI 算术表达式有优化空间，但已有多周期设计。**
   `fpga/mecanum/wheel_control_1khz.sv:17,49-57` 使用 48 位中间量，
   `p_product*10 + next_integral + signed_feedforward` 在一个状态内计算。
   新 PI 每路映射到 2 个 MULT27X36、3 个 MULTALU27X18；旧 PI 每路为 2 个 MULTALU27X18。
   建议将比例缩放、前馈合并与积分相加分级，按合法增益、目标、速度钳位范围证明各级所需位宽。
   不建议直接把全部 48 位变量改成 32 位：比例项和前馈的合法中间值可能超过 32 位。
   当前输出归一化已用 32 时钟恢复除法，不存在这里综合出宽组合除法器的问题。
   在 50MHz 下每 1ms 有 50000 时钟，允许增加几个计算阶段，仍能保持四轮并行 1kHz 更新。

4. **位置环已有较长组合路径，适合先拆级。**
   `fpga/mecanum/mecanum_pose_control.sv:83-84` 同拍处理四轮差分和四项求和/求差，
   旧时序报告最差 sys50 路径就是编码器位置到 `pose_loop/lateral_sum`，
   逻辑深度 20、数据延迟 17.542ns，50MHz 下 setup slack 2.388ns。
   建议分级锁存四轮差分、两两求和、最终求和，并保留同时采样语义；
   外环 100Hz 有充裕周期，不需把这些运算挤在单拍。
   这证明旧路径有改善空间，不代表新版的最差路径也一定相同；新版须用最终 P&R 报告确认。

5. **摄像头时钟约束是独立的时序余项。**
   旧结果有 camera_pclk_d 的 PR1014 普通布线警告及最小脉宽裕量 -0.849ns，
   `passed=false`，虽然 setup/hold 违例均为 0。
   应检查物理引脚、输入时钟网络、BUFG 约束和实际映射，不能只看 setup/hold 就称整机时序通过。
   现有证据没有建立此问题与位流生成超时之间的因果关系。

## 建议执行顺序与边界

先保存当前正在运行的冻结构建及最终报告；增加阶段诊断后，优先优化轮速估计流水和位置环求和流水，
再根据新版最差路径决定 PI 位宽/流水调整。每项改动分别比较资源、关键路径和构建耗时。
回归重点包括轮速估计换向/停转、四轮同步、PI饱和与积分、360/720度、长距离边界以及网络失联停车。

本次只读检查 RTL、综合网表、超时日志和历史时序报告，另写本检查记录及 audit.json。
未修改运行中构建的源码或约束，未启动第二个 Gowin 构建，未下载或驱动车辆。
上列优化建议尚未实施，不能声称已降低构建耗时或完成新版时序签核。
