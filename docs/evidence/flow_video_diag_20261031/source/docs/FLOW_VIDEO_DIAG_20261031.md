# 光流挂起与图传延迟诊断（2026-10-31）

本轮现场抓到了环境LK求解器未归还完成握手的状态；同时确认页面刷新节拍和Nano接收积压
分别造成低帧率显示和延迟。实车控制未启用，串口网关保持STOP。

## 已捕获的光流故障

只读诊断候选SHA256：`a02e0014731a1aac9be1035af11f62974406e0200957459b0f1c23a2edd14022`。
Place 2，Setup/Hold 0/0，最差Setup +0.002ns。MPW −0.688ns仍未决，整体时序未签核。
诊断没有增加自动重启；通过原CDC和事件通道发送约10Hz的OFDG包。

实际捕获内容：

| 字段 | 值 |
|---|---|
| 处理帧 / 网格点 | 28891 / (32,24) |
| grid状态 | WAIT_PATCH（2），busy=1 |
| grid当前状态等待 | 65535拍，已饱和 |
| patch状态 | IDLE（0） |
| patch busy / done | 1 / 0 |
| divider busy / done | 0 / 0 |
| patch启动 / 完成计数 | 83 / 82，计数按256回绕 |

因此上级在等待一个未到达的patch.done，除法器此时已不忙。
正常RTL在IDLE时应有busy=0；已观测组合违反这一不变量。
旧代码的default分支仅执行state<=IDLE，既不清busy，也不发done，会留下相同挂起状态。
状态寄存器直接异常落入合法IDLE也可能产生这一组合；不能仅凭最终状态断定最初一定执行了default。
需要同时覆盖非法编码退出和IDLE/busy矛盾，并保留异常证据。

原始包及其前序诊断已保存。网络中断造成采样空窗，所以“首个捕获到的挂起包”不是
故障发生那个时钟的记录。寄存器异常的物理触发、实现时序及PCLK影响仍待进一步验证，
没有据此宣布MPW是假违例或唯一根因。

## 视频延迟分层测量

| 测量配置 | PC收帧 | Nano完整帧 | 推理 | Nano落后PC帧数中位数 |
|---|---:|---:|---:|---:|
| 原接收路径，约19秒 | 29.97fps | 24.29fps | 24.08fps | 接收12 / 推理13 |
| 仅缩小接收缓冲，约19秒 | 29.69fps | 16.55fps | 16.50fps | 接收1 / 推理2 |
| 独立接收进程＋接收快路径，约29秒 | 29.94fps | 29.94fps | 29.94fps | 接收0 / 推理1 |

第三个窗口内环境流已经挂起，不能把它作为环境流正常满负载并发验收。
最终复测另行记录，以上原始对照窗口不覆盖改写。

1. 页面原先每200ms更新一次状态，并同时请求两张JPEG。浏览器5.0018秒内只有24次取图，
   实际约4.8fps，却显示后台29.79fps。现在图像走持续MJPEG连接，状态仍以200ms更新，
   重复状态刷新不重开视频连接。实测5秒150个不同帧，约29.91fps。
2. Nano UDP6102曾积压约8MB，系统RcvbufErrors累计明显非零。帧号差表明原路径约12帧积压，
   约400ms；完成组帧后的age_ms很小不能代表排队很少。
3. 单纯减小内核缓冲会随机丢掉图像行，导致更多整帧作废。512KiB实验降低排队，但完整帧率
   降到16.55fps，未作为最终方案保留。
4. 最终接收适配器复用缓冲区、减少逐包重复解析，将组帧与推理的Python执行分离，IPC只保留
   最新完整帧。Linux每32包采样一次SIOCGSTAMPNS以估计内核排队；积压超过80ms时快速丢弃
   旧排队包，从下一帧首行恢复，单独记录catchup事件和丢包量。对照窗口排队中位数约11ms。

本轮还两次直接观察到PC以太网Status=Disconnected，同时图传及SSH中断而IMU串口继续。
用户随后换线/固定连接。Nano恢复后链路为1000Mbps全双工，接口rx_errors为0；
这不等价于整段期间没有链路中断或没有UDP缓冲溢出。

## 接收代次与证据边界

新增接收适配器在真实静默后遇到帧号下降，使用两个完整、递增的新帧确认新代次。
覆盖新帧号已超过32以及旧帧号超过32768的情况；单个迟到旧帧不能替换当前代次。
正常连续16位回绕保留。没有启动ID的协议不能严格区分静默期间的正常回绕与设备复位，
因此这里只声明接收代次恢复，不把它当作设备重启证明。

冻结vendor算法保持原件，新的实时接收实现位于shared/live_capture.py和shared/capture_process.py。
PC只监听本机HTTP，Nano使用独立部署目录，模型引擎没有修改。
所有时延结论使用同主机队列时间或同一FPGA的帧号差，没有假定PC与Nano墙钟同步。

## 恢复候选及再次捕获

最终实验候选SHA256：`8a24d2496ccaf3f15f8a94c50551492a411b02298526e7bf48d15e647f1e1534`。
对应综合网表SHA256：`73261b889cf2bdd85886a8e9faeab62004acea6abff03f85b89badbf14c75c2d`。
已完成SRAM下载，未写Flash，未发送ARM或运动指令。Place 2 / Route 1 / TimingDriven 1，
Setup/Hold违例0/0，报告最差Setup为 **0.000ns**，不能描述为有充足正裕量。
本次只构建Place 2，不宣称在新诊断网表上完成2/3/4三组对照。
MPW −0.688ns仍未决；PR1014只保留既有B1接线的限定配置例外，未修改PLL约束掩盖问题。

`flow_lk_patch`现在对非法状态和`IDLE && busy`均通过FINISH返回一次无效完成，
解除上级等待，同时锁存首次异常的类型、当前状态和前一状态。没有用自动整机复位清掉证据。
最终固件上板后，该恢复分支已真实触发；首个带锁存标志的诊断上报帧为315，
锁存前态为 **WAIT_RAM(3)**，异常态为 **IDLE(0)**。该包已经是恢复后的采样，
不把其帧号或Nano墙钟当作异常边沿的精确时间。

RTL的WAIT_RAM应无条件进入LATCH(4)。对旧综合网表19个、新网表18个状态寄存器副本，
在所有副本一致编码为3、复位无效的假设下，按实际LUT INIT和CE做组合常量传播，
下一状态均为4。此检查只排查该条件下的组合方程，不证明所有可达状态、寄存器副本始终一致，
也不证明硬件时钟、复位、脉宽和电气条件正常。**最初异常跳转的触发原因仍未查明。**

## 最终显示路径

最终Nano新增只读`/infer.mjpg`，直接发送最新完成的检测帧；PC的同名路由在live模式
重定向到已配置的Nano地址，使视频显示与元数据缓存分离。
原NanoResults轮询目标是60Hz，没有固定10fps上限；100ms属于记录线程周期，
不能将其认定为检测显示瓶颈。这里保留的是独立视频流改动，不宣称修复了不存在的10fps限速。
实浏览器确认两路图像均加载为320宽；约6秒并发HTTP取流测得：PC视频30.003fps，
检测画面24.588fps，均无重复帧键。检测画面随实际推理速度刷新，未宣称其达到30fps。
检测线程仍受模型推理、反馈和事件解析等开销影响，本轮没有更换模型或模型引擎。
最终软件约59秒窗口内：PC/Nano收帧29.964/29.981fps、推理24.650fps，
接收/推理帧号差中位数1/3帧，排队中位数9.39ms；单次推理中位耗时34.30ms，
反馈错误0，PC/Nano不完整帧各增2。帧号差来自状态采样，不等价于玻璃到玻璃显示延迟。
浏览器约5秒观测到151次PC画面内容变化，两路图像均实际加载；没有据此声称检测显示30fps。

完成原始现场采集后，临时Nano包装器停止逐OFLW矢量的JSON落盘，保留低频诊断、状态及目标事件；
完整原文件保留在独立部署目录，不再持续以原速度增长。该包装器不包含明文令牌。
最终显示改动后的短窗口单独归档，不与上述五分钟窗口混算。
